# Semantic retrieval — verified implementation slice

Baseline: `SomeTests` at `1ca1d128fe3d3e0034335016a5d41f42eb998d22`. The independent embedding provider, bounded cache, and actual Gemini HTTP adapter live in `embedding.rs`, `semantic_memory.rs`, and `gemini_embedding.rs`.

## Runtime contract

- Lexical retrieval is the explicit default. To enable semantic retrieval in the normal CLI set `NEUROMITA_MEMORY_EMBEDDING_MODEL=gemini-embedding-001` or `gemini-embedding-2` and provide the existing `GEMINI_API_KEY`. The default embedding width is 768. Unknown model names are startup configuration errors, not an implicit downgrade. `KnowledgeRetrieval::semantic()` selects explicit semantic mode using any injected `EmbeddingProvider` (including future Python worker adapters).
- Embedding space identity includes **backend, model, protocol, and dimensions**. Gemini 001 sends `RETRIEVAL_QUERY` and `RETRIEVAL_DOCUMENT` task types; Gemini 2 sends different task-prefixed text and does **not** send `taskType`. The two spaces are incompatible. `GeminiEmbeddingProvider` sends `embedContent` for the query and `batchEmbedContents` in chunks of at most 64 documents. It validates HTTP, JSON, response count, vector width, finite elements, and nonzero norm. Similarity uses unit-normalized cosine. Authentication follows existing Gemini URL-query-key policy; errors drop the URL and `Debug` does not expose the key.
- `MessageHandler` prepares knowledge **asynchronously before calling `ResponseGenerator`**, never under the Character/Timeline lock, using one captured `CharacterContext`. `KnowledgeRetrieval` selects from snapshot-scoped records. `GenerationRequest` and the provider-neutral `GenerationInput` carry only the already rendered, bounded `prepared_knowledge`. Gemini and other generators do not perform retrieval.
- Topic query includes the input/guidance, working focus, reaction target and the latest three visible conversation messages; if completely empty it uses the character description. For embedding requests the input is bounded to 2048 Unicode scalar values; this is **not** a guarantee of the provider's token limit. Prompt records retain the existing strict **12 full records / 6000 Unicode scalar values** budget, with stable IDs, priorities and data-only delimiters. No silent content truncation of a memory record.
- **Timeline remains the only authority** for accepted memories. Membership comes from the `CharacterContext.memories` projection captured at the selected history prefix, never from the cache. Cache keys include CharacterId, EmbeddingSpace, MemoryId and exact text. Update/Merge with changed text causes a cache miss; Delete cannot return a deleted entry; a historical branch/fork gets its own membership and text version. Priority changes reuse the vector. No separate memory store, persistence or reindexing is required. Rebuilding/clearing the cache only changes retrieval cost.
- The cache is bounded, in-memory and FIFO (default CLI 512 document vectors). The query is always re-embedded; document vectors reuse exact-version entries. No network await while holding the cache mutex. No detached embedding task: cancelling the generation future drops pending provider calls; late document results cannot be admitted to the cache by a cancelled future.
- Embedding failure is a **visible generation error**, never a silent lexical fallback. This is a product policy; the user may explicitly choose lexical mode instead. TTS/acceptance semantics remain unchanged.

## Measured fixture quality and request cost

The deterministic **synthetic** fixture in `tests/semantic_retrieval.rs` gives the query `хочу согреться` and two memories: high-priority `картина` versus low-priority `ромашковый чай`. Neither has an exact matching query token. Lexical first rank is the unrelated high-priority memory; mocked semantic first rank is tea: **Recall@1 0/1 → 1/1** on this one synthetic case. This is an integration regression fixture, **not evidence of actual Gemini model recall**.

With two records, semantic cold lookup invokes **2 provider requests / 3 embedded texts** (one query, one document batch containing two records); warmed lookup invokes **1 request / 1 text**. Lexical uses **0 embedding calls**. A full cold set of 256 records through Gemini's 64-document batches would use 5 requests (1 query + 4 document batches); default 512-entry cache holds one such set, not every historical version. `RetrievalCost` also reports cache hits and submitted Unicode characters; `tracing` emits these counts, not memory content or secrets. Dollars, provider billing tokens and representative live-model quality have **not** been measured; no values are invented.

## Verification boundaries

- Rust unit and integration tests cover invalid vectors/width, two distinct Gemini protocols through loopback HTTP, topic-based selection, exact snapshot membership, content changes/fork/history, deletion/merge, multi-character isolation, cache rebuilding, deterministic tie breaking and prompt bounds, provider failure without fallback, and dropped/cancelled in-flight embed operations.
- `cargo test --locked --offline` tests provider behavior via local fixtures only. It does **not** send requests to the live Gemini API. Live model accuracy, remote quotas, actual cost/latency, token usage, multi-process index sharing and the future standalone Python embedding worker are not certified.
- Feature parity for TTL, RAG beyond long-term memories, knowledge graph, manual editor and model discovery is outside this slice. The cache is a small corpus exact cosine search, not an approximate ANN index; the domain cap is currently 256 live memories per character.

An opt-in live evaluation runner and its strict input contract are documented in [SEMANTIC_BENCHMARK.md](SEMANTIC_BENCHMARK.md). It uses the same production lexical shortlist and semantic retriever, but **does not certify live quality** without explicit credentials and labelled representative queries.

## Typed result, provenance and explicit filtering

`SemanticMemoryRetriever::retrieve_filtered` accepts an explicit `SemanticRetrievalFilter { minimum_cosine }` in the inclusive `[-1, 1]` cosine range; `retrieve` retains the original unfiltered behavior. Filtering is performed **after exact snapshot-member embeddings and deterministic semantic ranking**, but before the existing record/character prompt budget. A filter that excludes all candidates does not invoke lexical retrieval. Invalid thresholds are configuration errors before any provider calls.

`RetrievedMemory` now reports `status` (`EmptyCorpus`, `NoMatches`, `Selected`), the exact `EmbeddingSpace` (backend/model/protocol/dimensions), and ordered `matches` with Timeline `MemoryId` and cosine score for **only the records admitted to the final prompt**. This is memory-source provenance, not a claim of graph/history/document provenance, message-level ancestry or full RAG #22 parity. The authoritative membership and content still come solely from the captured Timeline projection; neither scores nor cache entries are durable facts. `EmbeddingError` remains an error rather than an empty successful result, with no hidden fallback. The default generation path does not apply an implicit score threshold.

## Deterministic multi-method fusion (opt-in, no model execution in validation)

`knowledge::retrieval_fusion::fuse` is a pure rank composition operation over already-scoped `RetrievalBucket`s. A hit is identified by `(CharacterId, RetrievalSource, opaque source ID)`; `Memory(7)` and `History(7)` cannot collide. The caller must supply facts from its captured authoritative source; the fusion module has no storage, background work, embedding generation or neural reranker. Cross-character candidates, duplicate method buckets, duplicate IDs within a method, inconsistent content/metadata and nonfinite scores are explicit errors. The returned `FusedHit` preserves source, content, per-method ranks/raw scores and metadata. Neither similarity from different embedding spaces nor heterogeneous FTS/keyword scores are treated as comparable.

Selection modes: `Union` merges all source keys and uses the sum of reciprocal 1-based ranks; `VectorOnly` admits vector keys only; `Intersect` requires an explicit minimum number of distinct methods, optionally vector; `TwoStage` admits vector keys only and enriches their evidence using other methods; `Rrf { k }` sums `1 / (k + rank + 1)` (zero-based rank) over present buckets. No mode implicitly falls back to another mode. Tie breaks are source-key-stable. Each method bucket and output limit is bounded; optional `minimum_graph` reserves *available* Graph hits from the candidate pool, without fabricating graph facts. No stochastic noise or cross-encoder is involved.

The existing `SemanticMemoryRetriever` uses the same composer in `VectorOnly` by default. `retrieve_with_fusion` adds a local lexical bucket using the existing `memory_context` token ordering, restricted to **actual token overlaps**. `KnowledgeRetrieval::semantic_fusion(retriever, mode)` is the explicit opt-in entry point; existing constructors and CLI behavior are unchanged. Filtering constrains the vector bucket, not the independent lexical bucket. Snapshot membership, record budgets, embedding error policy and cache lifetime do not change. Fusion does **not** turn one character's memory corpus into independently sourced history/graph retrieval: additional source adapters require separate authorization and source-specific read contracts.

All fusion tests are offline and deterministic. No live Gemini API, model loading or model-based reranking was performed for this extension. Full #22 source connectors, optional neural reranking, auto-versus-explicit search settings, and representative live quality remain separate work.

## Core / AI Engine ownership boundary

The Rust `knowledge` module owns immutable Timeline-scoped selection, lexical matching, deterministic cosine scoring, derived vector cache, source-aware fusion and bounded prompt composition. It accepts vectors only through the `EmbeddingProvider` port and never owns or loads neural model runtimes. The concrete Gemini embedding HTTP implementation resides in `adapters::gemini_embedding` and is selected only by the application composition root (`main.rs`); a future AI Engine subprocess can implement the same port without importing knowledge business rules. The LLM `GeminiProvider` is a regular `GenerationProvider`, not a universal response handler.

`request::MessageHandler` orchestrates context capture → knowledge selection → LLM provider → voice → acceptance. All awaits during knowledge selection occur within the existing request cancellation/selection watches. `ResponseGenerator` is provider dispatch only and cannot silently fall back to lexical on semantic failure. No parallel knowledge repository or event bus exists. The output is not an AI-generated fact and carries no model execution state.
