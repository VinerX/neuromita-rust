# SessionTimeline: знание возникает из наблюдения, а не из пересказа

**Статус:** обязательный инвариант от 2026-11-01, реализован для новых событий в Rust runtime. Ранее сохранённые базы, содержащие удалённый `EventObserved`, требуют явной миграции данных (не автоматического переноса знаний).

## Основной инвариант

Событие `X` — один канонический факт SessionTimeline. Мита знает `X` только если **непосредственно наблюдала само событие `X`** и это знание доступно в её текущем контексте (ветка, момент, последний reset). Адресация, участие в разговоре, причинные ссылки и чужие рассказы о `X` не делают Миту свидетелем `X`.

Если персонаж A рассказывает персонажу B о произошедшем `X`, сам рассказ — **новое событие `Y`**, например `Message` со `speaker = A` и `seen_by` с B. B знает **`Y`: «A рассказал мне о X»**, но не знает `X` как самостоятельно наблюдённый факт. Содержание `Y` может быть неполным, ошибочным или ложным; Timeline не приравнивает свидетельство A к наблюдению B.

```text
X: UnityEvent «дверь открылась»; seen_by = {A}
Y: Message «Я видела, как открылась дверь»; speaker = A; targets = {B}; seen_by = {A, B}

MitaView(A): X, Y
MitaView(B): Y     (НЕ X)
```

Если B пересказывает эту историю C, это новое сообщение `Z`; C узнаёт о `Z`, но не получает автоматически ни `Y`, ни `X`. Отношение `caused_by(X)` у `Y` (если оно вообще сохранено) **не даёт** слушателям доступа к `X`.

## Минимальные обязанности модели

- Общий доменный `Event` — контракт для любых событий, включая сообщения и Unity-события; `Message` специализирует `Event`, а конкретная структура сообщения реализует оба контракта. Это проектное направление; способ сериализации трейтов в Rust выбирается отдельно.
- У события одна идентичность (`EventId`) и фактические свидетели (`seen_by`). `targets` и `participants` у `Message` — маршрутизация и семантика разговора, **не** права знания.
- `SessionTimeline` хранит канонические события и рассчитывает `MitaView` по реальной видимости, ветке, срезу истории и reset. `MitaView` не копирует события в новую «истину».
- `ChatApi::react(event_id)` может реагировать на **любой** тип `Event`, но только когда этот конкретный `event_id` доступен отвечающей Мите в выбранном контексте; иначе отказ без вызова модели.
- `ChatApi::reply(message_id)` допустим только для известного `Message`. Сообщение игрока, сообщение Миты и последующий ответ — один доменный тип; Unity управляет последовательностью ходов. `initiate` не требует исходного события.
- Reset удаляет доступ к ранее известным событиям из **текущей** проекции знаний, не переписывая исторические факты и не создавая возможность заново «узнать X» через рассказ о нём. После reset новый рассказ `Y` остаётся только знанием `Y`.
- `reply_to`, `react_to`, `caused_by` и прочие ссылки описывают причинность, **не** распространение знания. Проекция не разыменовывает их для автоматического добавления недоступных фактов.

## Следствие для API и хранения

**Не нужен механизм «раскрыть старое событие X персонажу B» для передачи рассказа.** Чтобы B узнала о чём-либо, источник публикует самостоятельное событие, реально наблюдённое B. Для диалога это обычный `Message`. Не создаём отдельные `KnowledgeTransfer`, `LearnHistoricalFact` и дубликат `X`.

`EventObserved` и `disclose_conversation_message` удалены из runtime и публичного API. `knowledge_change` допускает получение только `fact.id` при непосредственном наблюдении; `CausalRelation::CausedBy` не переносит знание. SQLite индексирует тот же единственный факт. Старые тесты позднего раскрытия заменены тестами пересказов и reset.

## Обязательные тестовые сценарии при рефакторинге

1. `X` видела только A; A рассказывает B (`Y`): B может реагировать на `Y`, не может реагировать на `X`.
2. `Y` ссылается на `X` через causal link: это **не** раскрывает `X` B.
3. B передаёт пересказ C (`Z`): C видит `Z`, но не получает доступ к `X` или `Y`.
4. Если B сама наблюдала `X` непосредственно, её знание `X` не зависит от рассказа A.
5. После reset B не может использовать прежний `X`/`Y` в актуальном контексте; новая речь после reset создаёт новое событие, не восстанавливая старый `X`.
6. Тот же результат сохраняется после SQLite reopen, для fork-prefix и при проверке snapshot/context epoch.

**Закон проектирования:** `observed(event)` и `heard_a_message_about(event)` — разные факты. Их нельзя неявно отождествлять в Timeline, MitaView, Reply/React, persistence или LLM projection.

## Реализация и ограничения (2026-11-01)

- `domain::Event` задаёт общий типизированный интерфейс (`event_id`, `kind`, `witnesses`, `links`), реализованный `EventDraft`, `TimelineFact` и `ConversationMessage`.
- `conversation::Message: Event` добавляет `speaker`, `targets`, `participants` и `content`; специального storage для сообщений нет.
- `request::GenerationCommand` является **внутренним** контрактом исполнения; `ChatApi::send` не опубликован. Публичные операции `reply`, `react`, `initiate` не изменяют способ сохранения фактов.
- Сброс удаляет доступ к текущей проекции прежнего события, а новая реплика после сброса видна как новая реплика. Реставрация исходного EventId через пересказ запрещена.
- `Reply` принимает только `EventId` уже опубликованного и видимого `Message`, не создает `UserInput`; `React` принимает любой видимый `Event`, а `Initiate` не требует цели. Все три управляются Unity и сохраняют причинность на генерируемом сообщении; см. `CHAT_API.md`.
- TTS-конфигурация вынесена из request: `with_voice` удалён, исполнитель читает `VoiceSettings` по источнику запроса (launcher/game). Синтез речи остаётся внешним эффектом и не определяет доменный тип сообщения.

При изменении формата баз обязательна явная миграция или сознательное создание новой сессии. Перенос старых `EventObserved` в свидетельства наблюдения нарушил бы этот инвариант.
