# Long-term memory lifecycle (Core)

The authoritative data structure is `CharacterMemories`, captured and replayed by `SessionTimeline`. Knowledge retrieval receives only that captured projection; no new memory store, model or worker is introduced.

- Legacy JSON records (id, priority, content) decode as `kind=Fact`, `state=Active`, `expires_at_unix_ms=None`. Default values are omitted when writing them back. Legacy `MemoryChange::Delete` still means physical removal; existing Timeline events retain their original semantics.
- `MemoryState`: `Active`, `Forgotten`, `Deleted`. Ordinary prompt facts are active only. Forgotten facts are retained separately for future *explicit* recall; deleted records remain for inspection and explicit restore/purge, never prompt selection. No implicit restore occurs on a duplicate `Add`.
- `MemoryKind`: `Fact` or one of five island categories: `relationship`, `opinion`, `preferences`, `commitments_conflicts`, `language`. A character has at most one non-deleted record of each island category; `SetIsland` updates the stable ID of an active island. Islands are separate from the active-fact budget and prompt block. They are not embedded.
- Capacity: at most 256 active facts and 1,024 total retained records (including forgotten/deleted/islands). No eviction is performed as a write-side surprise. Exceeding a bound rejects the proposed write transaction.
- TTL is represented by an explicit expiration cutoff. `resolve_expirations(as_of_unix_ms)` deterministically proposes `Upsert(Forgotten)` changes; it does not commit anything. Callers must apply those changes through the existing guarded Timeline append. Reads never change history. No background TTL scheduler is claimed.
- `Forget`, `Restore`, `SoftDelete`, `SetExpiry`, `SetIsland` are explicit domain commands, distinct from the legacy LLM `memory_delete` operation. Updating existing IDs cannot change their kind. Purging corresponds to the legacy physical `Delete` operation; UI confirmation/backup workflows remain future scope.
- The request orchestration projects active islands into a bounded `[MEMORY ISLANDS]` data block and ranks ordinary active facts separately. The inference boundary remains `EmbeddingProvider` implemented outside the domain; island projection never invokes inference.

**Still outside this contract:** user-facing memory editor, timestamps and usage-frequency policy, recall authorization, and backup-before-purge. The standalone recall and periodic scheduler are described below; their presentation in UI and interaction with in-flight generation need separate contracts.

## Protected facts and startup maintenance

- `MemoryRecord.protected` defaults to false and is omitted from legacy JSON on serialization. Changes are made only via auditable `MemoryChange::SetProtection`, produced by `MemoryCommand::SetProtection`. Ordinary `Upsert` cannot silently change protection or mutate a protected record. Protected records cannot be forgotten, soft-deleted, purged, merged, or edited until explicitly unprotected.
- Protection is not inferred from `MemoryPriority::Critical`; priority and retention safety are separate concerns. This ensures no implicit protection of preexisting critical memories. An explicit administrative command is required to protect an existing record.
- An explicit `SessionTimeline::expire_character_memories(selection, character, as_of_unix_ms)` commits all eligible expirations in one guarded append. No expired candidates means no appended events. A stale selection fails before any append. Protection exempts records from the automatic pass.
- The Core startup orchestrator invokes the operation once per character using a single captured timestamp, **before** creating character workers. The periodic scheduler described below subsequently invokes the same guarded commit; neither path reads models or AI Engine or mutates memory on context reads.
- No user-facing protection control, backup, or recovery-before-purge is claimed. The current explicit `SetProtection` command is an internal domain contract; applying it from the UI will require a permission/confirmation boundary.

## Explicit Forgotten Recall and periodic TTL

- `knowledge::forgotten_recall::recall_forgotten` is a read-only, explicitly requested operation over an immutable `CharacterMemories` projection. It returns `character`, captured Timeline `anchor`, retained record IDs and lexical match counts. A text query must have searchable tokens and a caller-specified limit (1–12); only matching `Forgotten` facts are returned. An ID query accepts 1–12 specific forgotten-fact IDs and fails *as a whole* if any ID is duplicate, missing, active, deleted, or an island. No implicit restore, prompt injection, inference or vector cache access is performed.
- Ordinary lexical ranking, bounded prompt rendering and the direct semantic retriever explicitly reject non-active/non-fact records even if a caller supplies a mixed slice. Recalling old facts never makes them eligible for regular generation.
- `CharacterRegistry` owns a cancellable periodic TTL task (60-second interval) in the same owner lifecycle as character workers. It calls the existing guarded Timeline expiration operation with one captured clock reading for all characters; the domain remains clock-free and read-only code has no expiry side effects. Missed ticks are skipped rather than queued, a failed pass is logged, and shutdown cancels the task. Tests use a shorter injected interval. The startup pass remains synchronous.
- SQLite reopen tests check retained forgotten state and idempotent expiration, and both storage feature profiles run the same pure recall contract.

**Remaining work:** user-facing recall authorization and editor, confirmation/backup-before-purge, review of in-flight generation when a TTL commit changes its memory snapshot, and an optional explicit maintenance cadence setting. The new recall function is not wired to an automatic LLM path.

## Backup-first administrative purge and archive restoration

- `SessionTimeline::preview_memory_purge` selects at most 128 explicit `MemoryId`s in one character's current branch. It refuses empty/duplicate sets and refuses any record that is not `Deleted` and unprotected. The preview carries the original record values, selected branch, generation and HEAD. Preview is read-only.
- Internal `maintenance::purge_with_backup` requires explicit confirmation and a caller-supplied trusted backup path. It revalidates the exact preview, writes a full versioned JSON archive with character/branch/HEAD and source records, syncs it, and only then executes a guarded Timeline append of physical `MemoryChange::Delete` changes. Existing files, symlinks and failed writes are never overwritten and never trigger deletion. Files are owner-readable/writable (0600) on Unix; other platforms rely on OS ACLs. A storage concurrency failure after creating the backup retains the archive for inspection.
- Internal `maintenance::restore_from_backup` independently requires confirmation, validates the archive schema and compares every archived value against its canonical historical Timeline prefix. It rejects another branch, malformed/mixed/duplicate records or identities already occupied by newer data. On success it atomically reinserts records with state `Deleted`, without silently making them active in prompts. Restore remains explicitly separate from `MemoryCommand::Restore`.
- This is **projection purge**, not secure erasure: earlier append-only Timeline events, snapshots, branch forks and backups may still contain original content. Backup is sensitive plaintext; it must stay inside an access-controlled directory. Backup retention/deletion and true historical erasure require separate policy and implementation.
- The administrative boundary is **internal and not wired to a user-facing editor or LLM tool**. Authentication, authorization and actual user confirmation must be provided by a future UI/control layer. The core does not execute purge on timers, ordinary memory reads, model output or TTL. No AI Engine or inference dependency is introduced.
