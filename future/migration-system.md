## Контракты

| Примитив | Обязанности |
|---|---|
| VersionedData<Data> | Полный прочитанный документ/представление и его версия. Тип Data принадлежит модулю |
| MigrationSchema<Data> | Текущая версия и проверка данных поддерживаемых версий, включая промежуточные |
| MigrationStep<Data> | Исходная/целевая версии и детерминированное преобразование данных без внешних побочных эффектов |
| MigrationStore<Data> | read_versioned; commit(expected, next) с проверкой исходного снимка и атомарной записью данных вместе с версией |
| MigrationService<Data> | Проверка маршрута, prepare без записи, run с последовательным commit шагов |
| MigrationJob<Data> | Готовая привязка имени модуля, сервиса и его хранилища к startup |
| StartupMigrations | Явный упорядоченный список модулей, run до публикации Core API |

Migration<Input> сохранён как небольшой контракт преобразования внешнего формата. Он не заменяет MigrationService. RustSettingsMigration — форматный адаптер к общему сервису; PythonSettingsMigration — NotImplemented.

## Как подключить новый модуль

Модуль выбирает собственный Data, реализует MigrationSchema, шаги MigrationStep и адаптер MigrationStore. Конструирует MigrationService::new(schema, steps), затем регистрирует service.into_startup("module-name", store) в ApplicationConfig.migrations. Менять общий исполнитель, добавлять тип модуля в enum или переписывать его предметные операции не требуется. Владельцы/потребители открывают данные после завершения миграций; их обычные операции используют актуальную модель.

MigrationService не зависит от settings, JSON, Timeline или конкретной БД. Хранилище отвечает за свою транзакцию и исключение писателей. Data может быть документом либо предметным представлением для конкретного storage adapter; исполнитель не требует загружать историю всего приложения.

## Порядок и ошибки

Версии и переходы фиксируются при создании сервиса. Шаг должен увеличивать версию и не превышать текущую; два исходящих шага одной версии отвергаются. До изменения данных проверяется весь путь. Более новая неподдерживаемая версия, пропущенный шаг и неправильные данные дают ошибку. Автоматического выбора первой миграции или обхода пропуска нет.

prepare выполняет ту же цепочку, что run, но не получает хранилище и ничего не фиксирует. run читает исходный снимок, проверяет его, преобразует один шаг, проверяет результат и вызывает commit. Удачный commit делает данные и версию видимыми вместе. При ошибке commit хранилище обязано сохранить предыдущий снимок. При Conflict исполнитель не перечитывает молча данные и не повторяет шаг внутри этого запуска.

После сбоя повторный запуск читает фактическую последнюю версию. Зафиксированные шаги не повторяются, незаписанный шаг может вычисляться повторно. Поэтому отправка HTTP-команд, файловые side effects или уведомление клиентов не должны выполняться внутри MigrationStep. Полностью актуальные валидные данные не переписываются.

StartupMigrations выполняет модули в порядке регистрации и останавливается на первой ошибке с именем модуля. Дубликат имени отвергается до запуска. Нет глобального service locator, автопоиска, dependency resolver или общей транзакции между разными хранилищами. Завершённый модуль сохраняет свою версию, если следующий модуль упал; его повторный run будет проверкой без миграционных записей.

## Bootstrap

ApplicationLifecycle сначала резервирует единственный runtime slot. Для SettingsSource::Stored автоматически ставится обязательный settings job, затем выполняются ApplicationConfig.migrations в заданном порядке. Всё выполняется в spawn_blocking до SettingsLifecycle::prepare, bind listener, запуска workers и публикации API. Source::Initial — явное создание актуальных данных, а не миграция существующего файла.

Ошибка останавливает запуск, не публикуя API. Если future запуска отменён во время блокирующего job, runtime lease остаётся у выполняющейся задачи до её завершения: следующий start получает Busy, а старое выполнение не пересекается с новым Core. Уже начавшийся атомарный commit не прерывается посередине.

SettingsRepository::migrate — обязательный startup-контракт адаптера настроек. JsonSettingsRepository делегирует общему MigrationService и реализует MigrationStore<Vec<u8>>; MemorySettingsRepository проверяет уже типизированные текущие данные. Обёртки репозитория явно делегируют migrate. Обычный load остаётся чтением без изменения файла, в том числе для offline export.

## Файловые гарантии настроек

Все записи JsonSettingsRepository используют стабильный соседний settings.json.lock и [std::fs::File::lock](https://doc.rust-lang.org/std/fs/struct.File.html#method.lock). Миграционный commit под тем же lock перечитывает и сравнивает полный исходный документ, затем заменяет файл через уникальный temp, sync и rename. Нельзя удалять sidecar при работающих писателях: его постоянное имя обеспечивает общую точку блокировки. Сравнение версии без сравнения данных недостаточно.

Контракт кооперативный: внешние редакторы, которые игнорируют lock, не получают взаимного исключения. Отдельная crash recovery для незафиксированных temp и power-loss durability каталога не реализованы; temp не является источником версии. Текущие SQLite-миграции не переписывались: новый модуль может подключить собственный adapter по тем же контрактам.
